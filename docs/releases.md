# Release Process

This repository publishes the locally maintained receivers as individual Go
modules. The release tooling follows the same core pattern used by
`open-telemetry/opentelemetry-collector-contrib`: `chloggen` collects release
notes, `versions.yaml` defines module sets, and `multimod` verifies and creates
the module tags.

The collector distribution itself is generated from `builder-config.yaml` during
local builds and CI. The local receiver entries in that file intentionally use
`v0.0.0` plus local `replace` directives so development builds use the checked
out receiver sources.

## Receiver Module Tags

The receivers live in nested Go modules under `receivers/`, so their semantic
version tags must be prefixed with the module directory:

```text
receivers/stackdriver/v0.1.0
receivers/yace/v0.1.0
```

Do not use a repository-root tag such as `v0.1.0` for receiver module releases.
Go resolves versions for nested modules from the directory-prefixed tags.

## Changelog Entries

This repository uses `go.opentelemetry.io/build-tools/chloggen` to collect
release notes for user-visible changes. The setup follows the lightweight
version of the changelog process used by
`open-telemetry/opentelemetry-collector-contrib`.

User-visible changes should include a changelog entry in the same pull request
as the change:

```bash
make chlog-new NAME=<short-entry-name>
```

Edit the generated `.chloggen/<short-entry-name>.yaml` file and choose one of
the components listed in `.chloggen/config.yaml`. Internal maintenance-only
changes may omit a changelog entry.

Validate entries before merging:

```bash
make chlog-validate
```

Preview the generated changelog text without modifying files:

```bash
make chlog-preview
```

## Updating the Changelog

When preparing a release, update `CHANGELOG.md` from the pending entries:

```bash
make chlog-update VERSION=v0.1.0
```

Open the release preparation pull request with the `CHANGELOG.md` update and
the deleted `.chloggen/*.yaml` entry files generated by `chlog-update`.

## Automated Release PR

Use the `Automation - Prepare Release` workflow to create the release
preparation pull request. Run it from GitHub Actions with the target release
version, including the leading `v`:

```text
v0.1.0
```

The workflow creates a `prepare-release-prs/<version>` branch, updates
`versions.yaml`, runs `make chlog-update VERSION=<version>`, validates the
changelog and module set, commits the result, pushes the branch, and opens a
pull request.

## Preparing a Release

1. Choose the next receiver module version.
2. Run the `Automation - Prepare Release` workflow with that version.
3. If a new receiver module was added, add its module path to the same module
   set.
4. If preparing the release manually instead of using the workflow, update
   `versions.yaml` and `CHANGELOG.md`:

   ```bash
   make chlog-update VERSION=v0.1.0
   ```

5. Open or review the pull request with the `versions.yaml` and changelog
   changes.
6. Before merging, run:

   ```bash
   make chlog-validate
   make multimod-verify
   make test
   make check
   ```

7. Merge the pull request after CI passes.

## Tagging a Release

After the release preparation pull request is merged, update your local `main`
branch and tag the merge commit:

```bash
git checkout main
git pull --ff-only origin main
make push-tags MODSET=receivers COMMIT=<merge-sha>
```

`make push-tags` verifies `versions.yaml`, asks `multimod` for the module tags in
the selected module set, and pushes each tag to the configured remote. It
defaults to `REMOTE=origin`; override it if needed:

```bash
make push-tags MODSET=receivers COMMIT=<merge-sha> REMOTE=<remote-name-or-url>
```

To verify the pushed tags:

```bash
git ls-remote --tags origin 'receivers/*/v0.1.0'
```

## Prerelease Helper

The Makefile also exposes the upstream `multimod prerelease` helper:

```bash
make multimod-prerelease MODSET=receivers
```

Use this only when you want `multimod` to update intra-repository module
dependencies for a release. The current receiver modules do not depend on each
other, so a normal receiver release usually only needs the manual
`versions.yaml` update followed by `make push-tags` after merge.
